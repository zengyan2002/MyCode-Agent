# 团队成员忙碌期间消息处理修复 Spec

审批状态：用户已于 2026-09-13 批准，随后统一批准其余三份文档并要求开始实现。现已完成本机验收，证据和平台限制见 checklist.md。

## 背景

团队成员通过持久化邮箱通信。发送者可以要求唤醒接收者，但当前忙碌成员会跳过唤醒，完成本轮后又先等待通知再读取邮箱，导致已经送达的消息可能长期滞留。

同一条链路还存在相关缺陷：成员处理结束后的消费确认参数不匹配；消费位置按确认时的邮箱末尾推进，可能跳过处理期间新来的消息；同进程通知消费后没有清除；独立窗格成员的发送入口没有接入唤醒处理。

## 目标

- A 给正在工作的 B 发送消息并要求唤醒后，B 正常完成当前一轮，再自动处理该消息，无需用户或其他成员再次唤醒。
- 修复消息到达、成员进入等待和消费确认之间的衔接，避免消息被跳过或成员无事可做时反复循环。
- 保持成员逐轮执行，不打断正在进行的模型请求或工具操作。

## 方案比较

1. 推荐：当前一轮结束后处理积压消息。修复通知保留、等待前检查和消费确认，沿用现有逐轮执行方式，改动集中在成员通信链路。
2. 在本轮的下一次模型请求前注入消息。反馈更及时，但需要进一步调整成员执行循环和消息确认时机，本次不采用。

## 功能需求

- F1：发送者要求唤醒时，忙碌的接收成员必须在当前一轮成功结束后自动处理已投递的消息；不同时启动该成员的第二轮执行。
- F2：接收成员准备进入空闲等待时到达的唤醒消息仍须被处理，不得依赖另一次发送才能继续运行。
- F3：成员成功处理一批消息后，只确认这一批已经处理的消息。处理期间新到的消息保持未读，并在后续轮次处理。处理失败时不确认该批消息；允许按已有恢复流程再次处理，不承诺外部操作恰好执行一次。
- F4：空闲成员收到要求唤醒的消息后自动处理。未要求唤醒的消息不单独唤醒已处于空闲等待的成员；成员因其他原因开始下一轮检查时可以一并处理积压消息。
- F5：通知被消费且邮箱没有未读消息时，成员重新等待，不因残留通知持续循环或重复调用模型。多个通知可以合并，但不能因此跳过不同消息。
- F6：上述行为适用于现有同进程、tmux 和 iTerm2 成员运行方式，包括成员向成员发送消息的入口。已结束成员不因普通消息被自动重建；保留已有投递结果表达方式。

## 非功能需求

- N1：继续使用已有团队消息格式和持久化邮箱；既有邮箱与消费位置记录能够继续读取。
- N2：模型和工具执行期间不持有邮箱写锁；空闲等待不能持续占用执行循环。
- N3：并发测试通过明确控制消息投递和轮次结束顺序验证行为，避免仅靠固定延时猜测执行顺序。
- N4：代码直接描述通知、消息读取和消费确认的实际行为，不为测试额外增加生产工厂、包装层或可替换接口。

## 不做的事

- 不在当前模型请求或工具操作中途强制打断成员。
- 不补齐自主任务扫描、无人认领事件和依赖解除后的任务调度。
- 不修改 Session 的保存时机，不引入数据库或消息队列服务。
- 不实现进程崩溃后的工具副作用回滚、跨文件事务或恰好一次处理保证。
- 不扩展 Lead 的消息处理时机；共用消费确认逻辑改动需保持其现有调用可用。
- 不自动恢复已经失败或终止的成员。

## 验收标准

- AC1（F1）：控制 B 停留在当前轮次，A 投递并要求唤醒；当前轮次未结束时 B 不开始第二轮；放行后 B 自动收到消息，期间没有额外唤醒。
- AC2（F2）：分别在等待前检查阶段和已经等待时投递唤醒消息，两种情况下 B 均能自动处理。
- AC3（F3）：B 读取第一条消息并开始处理后再投递第二条；确认第一条后，第二条仍可读取并在后续轮次处理。
- AC4（F3）：消息处理抛出错误后，重新读取邮箱仍能取得该批消息；正常处理后再次读取不返回已确认消息，且消费确认不因参数类型错误失败。
- AC5（F4）：空闲 B 收到不要求唤醒的消息后保持等待；随后收到显式唤醒，再处理积压消息。
- AC6（F5）：一次或多次唤醒对应的消息处理完毕后，B 回到可阻塞的等待状态，不额外调用模型，不持续执行空循环。
- AC7（F6）：验证三种后端的通知与等待衔接，以及独立成员的实际发送装配入口；只模拟不可用的外部终端命令时，在验收报告中明确标注，不能报告为真实终端端到端通过。
- AC8（F6）：对已结束成员投递消息不会重建成员或开始新一轮；现有默认不唤醒、名称寻址和消息协议权限测试继续通过。
- AC9（N1、N2、N3、N4）：旧邮箱和消费记录仍可读取；成员处理消息期间其他成员能够继续投递；相关回归测试通过，并报告检查范围及无法实测的平台限制。
